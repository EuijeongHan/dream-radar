## 2. 다시 보다가 찾아서 **고친** 것 5건

### 2.1 ★ 라벨링 테스트 17개가 가짜로 통과하고 있었습니다

`load_candidates(date, candidates_dir: Path = CANDIDATES_DIR)` 처럼 **기본 인자에 모듈
상수를 직접 썼습니다.** 기본값은 함수 정의 시점에 바인딩되므로, 테스트가
`monkeypatch.setattr(L, "CANDIDATES_DIR", tmp)` 로 갈아끼워도 **실제
`data/candidates/2026-08-12.jsonl`(719건)을 읽고 있었습니다.**

테스트가 12건을 기대했는데 719건을 읽고도 통과한 건, 입력 키가 12개에서 끊기자
`q`로 종료돼 12건만 기록됐기 때문입니다. **우연히 초록색이었습니다.**

→ 경로 인자를 전부 `None` 기본값으로 바꾸고 호출 시점에 해석하게 고쳤습니다.
   고치자 `test_shuffle_actually_shuffles`가 즉시 빨간불이 됐고, 그게 정상입니다.

가장 무서운 종류의 버그라 맨 앞에 적습니다. **통과하는 테스트가 아무것도 검증하지
않고 있었습니다.**

### 2.2 ★ 규칙 검증자가 정상 요약을 0.3점으로 떨어뜨렸습니다

델타 §D6.4의 "초록에 없는 숫자가 요약에 있으면 감점"을 문자 그대로 구현했더니,
**정상 요약이 0.3점을 받았습니다.**

원인은 교차언어입니다. 영어 초록은 작은 수를 **단어로** 씁니다 — `"six object
detection models"`. 한국어 요약은 같은 내용을 **숫자로** 씁니다 — `"모델 6종"`.
그래서 `6`, `2단계`의 `2`, `YOLOv5`의 `5`가 전부 "초록에 없는 수치"로 잡혔습니다.

→ 검사 대상을 **소수·백분율·세 자리 이상**으로 좁혔습니다. 성능 수치는 거의 항상
   이 셋 중 하나이고, 맨 두 자리 정수는 개수·차수·모델 버전입니다.
   `"500장으로 학습"` 같은 조작은 그대로 잡힙니다.

**이건 규칙 검증자만의 문제가 아닙니다.** LLM 검증자도 같은 교차언어 조건에 놓입니다 —
§3.1 참조.

### 2.3 `profile.papers.ko` 경로를 한 군데 하드코딩했습니다

결정_M0 §4를 지적받고 `resolve_profile()`을 만들어 놓고도, `test_profile_parity`에서
`DATA_DIR / "profile.papers.ko.yaml"` 로 직접 읽고 있었습니다. 나중에
`profile.papers.ko_1.yaml`이 생기면 **테스트는 통과하는데 실제 대조군은 다른 파일**이
되는 최악의 상태가 됩니다. `load_profile("profile.papers.ko")` 로 고쳤습니다.

### 2.4 arXiv 구형 ID에서 아카이브 접두사가 날아갔습니다

`raw_id.rsplit("/", 1)[-1]` 로 ID를 뽑았는데, 2007년 이전 형식
(`http://arxiv.org/abs/math.GT/0309136v1`)에서는 `math.GT/`가 잘려나가
`arxiv:0309136` 이 됩니다. 다른 아카이브의 같은 번호와 충돌해 **중복 제거가 조용히
틀립니다.** `/abs/` 뒤 전체를 쓰도록 고치고 회귀 테스트를 넣었습니다.

`sortBy=submittedDate` 로만 조회하므로 실제로 나올 확률은 낮습니다. 다만 조용히 틀리는
종류라 고쳤습니다.

### 2.5 후보 파일에 중복 줄이 생길 수 있었습니다

`run_collect`는 후보 파일에 쓰고 **그다음에** state.db에 마킹합니다. 그 사이에 죽으면
다음 실행이 같은 아이템을 한 번 더 씁니다. 그 상태로 라벨링하면 같은 논문이 두 번
나오고, 두 판정이 엇갈리면 골드셋이 조용히 오염됩니다.

→ 순서를 바꾸는 대신(그러면 크래시 시 아이템이 영구 유실됩니다) **읽는 쪽에서 접도록**
   했습니다. 후보 파일 자체는 이력이므로 고치지 않습니다.

## 3. 안 고치고 남긴 것 — 본인 판단 필요

### 3.1 ★ 요약 출력 언어가 M2 지표를 교란합니다

`paper.md`에 출력 언어 지시가 아예 없었습니다. 지시가 없으면 모델이 매번 다르게
고르므로 일단 `{output_language}` 자리표시자를 넣고 기본값을 **한국어**로 뒀습니다
(텔레그램·사이트 독자가 본인이므로).

**문제는 이 선택이 M2 DoD에 직접 영향을 준다는 것입니다.**

초록은 영어, 요약은 한국어 → 검증자가 교차언어로 대조해야 합니다. 교차언어 판정은
동일언어 대비 약합니다. **faithfulness가 낮게 나와도 요약이 나쁜 건지 검증이 약한
건지 구분되지 않습니다.** 임계 0.7과 재생성률이 전부 이 교란 위에 얹힙니다.

제안: M2에서 **같은 초록에 한국어/영어 요약을 각각 생성해 faithfulness를 비교**하는
조건을 넣으세요. M1의 영/한 프로파일 비교(기획안 §7-(2))와 **정확히 같은 구조의
실험**이고, 추가 비용은 요약 20건어치입니다. 결과가 어느 쪽이든 포트폴리오에 씁니다.

- 차이가 크면 → "교차언어 검증의 손실을 실측했다"
- 차이가 없으면 → "한국어 출력이 지표를 훼손하지 않음을 확인했다"

`schema.OUTPUT_LANGUAGES`가 두 값을 다 들고 있는 이유입니다. **결정해 주세요.**

### 3.2 서베이를 관련으로 볼 것인가 (라벨링 기준 §4)

`profile.papers_1.yaml`에서 서베이는 `penalty: 0.3` 으로 감점이 가장 약하고
*"분야 입문에 유용"* 이라고 적혀 있습니다. 그런데 골드셋은 이분법입니다.

하루에 여러 건 나오고, **판정이 흔들리면 라벨 일관성이 가장 크게 깨지는 항목**입니다.
라벨링 **시작 전에** 정하세요. 중간에 바꾸면 앞뒤 라벨의 기준이 달라집니다.

### 3.3 M1 임베딩 의존성을 설치할까요 (약 5GB)

M1은 `bge-m3` 로컬 임베딩 + `bge-reranker-v2-m3` 리랭커입니다(델타 §D6.3).
`torch` + `sentence-transformers` 약 2~3GB, 모델 가중치 약 2.3GB.

**설치는 안 했습니다.** 되돌리기 번거로운 용량이고 본인 맥이라 승인을 받는 게 맞다고
봤습니다. 승인해 주시면 골드셋이 나오기 전에 미리 받아두겠습니다 — 다운로드가
M1에서 가장 오래 걸리는 부분입니다.

## 4. 다음 마일스톤에 영향을 주는 설계 우려

### 4.1 ★ M3에서 아이템이 영구 유실될 수 있습니다

지금 `collect` 단계가 state.db에 `seen`을 마킹합니다. M0에서는 맞습니다 — 수집이
곧 끝이니까요.

그런데 M3에서 전 구간(`--stage full`)을 돌리면 **수집 직후 마킹**되고, 이후 랭킹·요약·
발행 중 하나라도 실패하면 그날 아이템은 이미 `seen`이라 **다시는 후보에 오르지
않습니다.** 하루치가 조용히 사라집니다.

Actions 크론이 매일 도는 구조라 실패는 반드시 일어납니다(기획안 §11이 이미 지연·실패를
전제하고 있습니다).

→ 제안: `seen_items`를 **수집 완료**와 **처리 완료** 두 상태로 나눕니다.
   수집 시 `collected`로 넣고, 발행 성공 시 `published`로 승격. 다음 실행은
   `published`가 아닌 것을 다시 후보에 넣습니다.

M3 착수 시점에 결정하면 됩니다. 지금 고치지 않은 이유는 M0 DoD가 이미 통과했고,
스키마 변경이 M3의 설계 결정과 함께 가야 하기 때문입니다. **잊지 않도록 여기 적어둡니다.**

### 4.2 날짜별 후보 수가 크게 다릅니다 — M1 지표 해석에 영향

오늘 수집분을 실측했습니다.

```
수집 719건 / published 범위 2026-08-10T05:30Z ~ 2026-08-11T17:59Z (실제 36.5시간)
```

48시간 창인데 실제 span이 36.5시간인 건 정상입니다 — arXiv 제출·공개 스케줄에 공백이
있습니다. 창은 정확히 소진됐습니다(가장 오래된 항목이 컷오프 직전).

문제는 **첫날만 719건이고 둘째·셋째 날은 절반 수준**이 된다는 것입니다. 첫 실행은
48시간을 통째로 가져가고, 이후는 중복 제거 후 신규분만 남기 때문입니다.

→ M1에서 Hit@5를 **날짜별로 내고 평균**낼 때, 후보 풀 크기가 2배 차이 나는 날을 섞게
   됩니다. 큰 풀에서의 Hit@5가 구조적으로 불리합니다. 지표를 낼 때 **날짜별 후보 수를
   함께 표에 넣으세요.** `eval/results.md`에 후보 수 열이 없으면 나중에 해석이 안 됩니다.

### 4.3 설정에 없는 카테고리가 섞여 들어옵니다 (정상 동작)

primary category 분포를 봤더니 설정하지 않은 것들이 있습니다.

```
cs.CV 210 · cs.LG 138 · cs.AI 133 · cs.CL 88 · cs.IR 23 · cs.RO 19 · cs.CR 15 · cs.SD 9
```

`cs.RO`(로보틱스)·`cs.CR`(보안)·`cs.SD`(음성)는 프로파일에 없습니다. arXiv의 `cat:`
질의가 **교차 등록(cross-list)을 포함**하기 때문입니다 — primary가 cs.RO이고 cs.AI에
교차 등록된 논문이 걸립니다.

**버그가 아닙니다.** 그리고 프로파일 `exclude.soft`에 `"robotics control"`이 이미
penalty 0.8로 있으니 랭킹이 처리합니다. 다만 **골드셋 라벨링 중에 로보틱스 논문이
나와도 당황하지 마세요.** 무관으로 찍으면 됩니다.

### 4.4 규칙 검증자로는 M2 DoD를 판정할 수 없습니다 (설계상 정상)

기획안 §8 M2 DoD는 *"왜곡 3건을 검증자가 **모두** 잡아낸다"*입니다.
`RuleBasedFakeVerifier`는 ① 수치만 잡고 ②③은 못 잡습니다.

이걸 규칙으로 흉내 내지 않은 건 의도입니다. **제가 왜곡 샘플도 쓰고 규칙도 쓰면,
규칙이 제 샘플을 잡는 건 당연하고 아무것도 증명하지 못합니다.**
`test_rulebased_verifier_misses_semantic_distortions`가 이 실패를 고정해서, 나중에
누가 규칙을 덧붙이면 빨간불이 나고 "샘플에 과적합된 것 아닌가"를 되묻게 됩니다.

DoD 판정 테스트(`test_llm_verifier_catches_all_three_distortions`)는 키가 없어 skip
상태입니다. **키가 오는 날 구현체만 갈아끼우면 그날 판정됩니다.**
