# 04 — 수집분 오브젝트 스토리지 증분 적재

작성 2026-09-07 · 구현 `src/storage/` · 테스트 `tests/test_storage_sync.py`

> 기획안_2에 없는 추가 작업입니다. 착수 전 `docs/작업규약.md` §3의 **T7**(스펙에 없는 설정 항목)과
> **T11**(§3 목록에 없는 외부 도메인)에 걸려 사용자 승인을 받았습니다. 승인 범위는
> **papers 채널의 `data/candidates/` 증분 적재와 복구**입니다.

---

## 1. 왜 하는가

`data/candidates/` 는 gitignore입니다. **이 머신이 죽으면 수집분이 사라집니다.**
`state.db`에 id는 남지만 제목·초록은 후보 파일에만 있고, arXiv 수집 창은 48시간이라
과거분은 같은 쿼리로 다시 오지 않습니다. 즉 재수집으로 복구되지 않습니다.

현재 보존 대상은 **1,851건 / 3.8MB** 입니다.

```
data/candidates/2026-08-12.jsonl    719줄  1.5MB
data/candidates/2026-08-18.jsonl  1,132줄  2.3MB
```

## 2. 키 구조

Hive 스타일 파티션입니다. 날짜가 키에 들어가므로 같은 날 재실행은 같은 키를 덮어씁니다.

```
{prefix}/channel=papers/dt=2026-08-18/candidates.jsonl
```

후보 파일은 append-only라 재실행하면 줄이 늘 수 있습니다. 그때만 해시가 바뀌어
다시 올라갑니다.

## 3. 증분과 복구 — 세 갈래 ★

매니페스트(`data/s3_manifest.json`, gitignore)에 키별 sha256을 남깁니다.

| 상태 | 판정 | 왜 |
|:--|:--|:--|
| 로컬 해시 == 매니페스트 해시 | **건너뜀** | 증분 적재 |
| 로컬 해시 != 매니페스트 해시 | **재업로드** | 파일이 자랐음 |
| 매니페스트에 없음 | **원격 `head` 확인 후 결정** | 실패 복구 |

**매니페스트는 백엔드별로 구분합니다.** 항목에 `backend`(`s3:버킷명` / `local:경로`)를
남기고, 다르면 "기록 없음"으로 봅니다. 안 그러면 `RADAR_MODE=fake` 로 한 번 돌린
머신에서 진짜 버킷으로 바꿨을 때 매니페스트가 "이미 올렸다"고 답해 **버킷이 영원히
비어 있게** 됩니다. 구현 중 실제로 이 상태를 만들었다가 잡았습니다.

세 번째가 핵심입니다. 매니페스트만 믿으면 파일 하나 지워진 걸로 매일 수 MB를 다시
올립니다. 원격에 같은 해시가 있으면 **네트워크를 타지 않고 기록만 되살립니다**
(`recovered` 카운트).

무결성 비교에 **ETag를 쓰지 않습니다.** 멀티파트 업로드에서 ETag는 MD5가 아니게 되어,
작은 파일에서는 맞다가 파일이 커지는 순간 조용히 어긋납니다. 우리가 붙인
`radar-sha256` 메타데이터를 씁니다.

## 4. 유출 게이트 — 내용을 본다

CLAUDE.md §3-3(채용공고 공개 게시 금지)에 걸리지 않도록, **업로드 직전에 줄 단위로**
검사합니다.

```
줄의 channel 이 인자와 다르면        → SyncRefused
publish_scope 가 public 이 아니면    → ScopeViolation (gates.assert_public_scope)
JSON 파싱 실패                       → SyncRefused (무시하지 않는다)
```

파일명이나 CLI 인자가 아니라 **내용**을 봅니다. 인자는 오타가 나고 내용은 거짓말을
하지 않습니다. 재사용 규칙 R5대로 게이트를 "존재"시키지 않고 **호출**합니다.

`--channel` 은 argparse choices로 `papers` 만 받습니다. jobs 는 CLI 단계에서 막힙니다.

## 5. 자격증명 — 코드에 없다

CLAUDE.md §3-2. 이 저장소는 public입니다.

`S3ObjectStore` 는 **키를 인자로 받는 생성자를 두지 않았습니다.** 받을 수 있으면
언젠가 설정 파일에 적히고, 그 파일이 커밋됩니다. boto3 기본 자격증명 체인만 씁니다.

```bash
export RADAR_S3_BUCKET=your-bucket-name    # 필수. 없으면 exit 1
export RADAR_S3_PREFIX=radar               # 선택 (기본 radar)
# 자격증명은 ~/.aws/credentials 또는 AWS_ACCESS_KEY_ID/SECRET 환경변수
```

**버킷 미설정 시 조용히 건너뛰지 않고 exit 1 입니다.** 건너뛰게 두면 크론이 매일
아무것도 안 올리고 초록불을 냅니다 — `config.radar_mode()` 기본값이 fake가 아닌 것과
같은 판단입니다.

## 6. 의존성 — Actions에는 설치하지 않는다

boto3는 `requirements-s3.txt` 로 분리했고 지연 임포트입니다.
botocore가 100MB에 가까워, 수집만 하는 `daily-papers` 크론이 매일 받을 이유가 없습니다
(`requirements-eval.txt` 약 1GB를 Actions에서 제외한 것과 같은 판단).

## 7. 실행

```bash
python -m src.storage.sync --channel papers --dry-run   # 계획만
python -m src.storage.sync --channel papers             # 적재
RADAR_MODE=fake python -m src.storage.sync --channel papers   # 로컬 스토어(테스트)
```

Airflow DAG `radar_papers` 에 `collect >> sync_s3` 로 붙어 있습니다.
**파이프라인 끝이 아니라 collect 직후**입니다 — 랭킹·요약이 실패해도 수집분은 이미
보존됩니다.
