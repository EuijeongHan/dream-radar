> **기획안 v1.0 / 2026-08-12 / 한의정**
> 이 문서는 Claude Code에 그대로 전달해 구현을 시작하기 위한 스펙입니다.

## 0. 이 문서 사용법 (Claude Code용)

- 이 문서는 **확정된 설계**입니다. 기술 선택 근거가 §4에 있으니, 바꾸려면 근거를 먼저 반박하세요.
- 구현은 §8 마일스톤 순서대로 진행합니다. **각 마일스톤의 DoD를 만족하기 전에 다음으로 넘어가지 마세요.**
- §3(법적 제약)은 협상 대상이 아닙니다. 크롤링 금지 목록에 있는 사이트는 어떤 우회 방법으로도 접근하지 않습니다.
- 모든 실행은 `data/runs.jsonl`에 원장으로 남깁니다. 이 원장은 나중에 포트폴리오 근거 자료가 되므로 스키마(§7)를 임의로 바꾸지 마세요.
- 애매한 판단이 필요하면 구현을 멈추고 질문하세요. 추측으로 채우지 마세요.

## 1. 목적

**두 가지를 동시에 달성합니다.**

| | 목적 | 성공 기준 |
|:--|:--|:--|
| 실사용 | 매일 아침 논문 5편 + 신규 채용공고 요약을 받는다 | 3개월간 자동 실행, 실제로 읽게 되는 수준의 선별 품질 |
| 포트폴리오 | "도메인 무관 문서 파이프라인 + 검증 설계" 역량 증명 | 랭킹 성능 정량 측정치 + 90일 자동 커밋 이력 + 공개 저장소 |

**포트폴리오 관점의 핵심 주장**은 "arXiv 요약 봇을 만들었다"가 아니라 다음 세 가지입니다.

1. **선별 문제를 검색 문제로 정의하고 정량 평가했다** — 하루 수백 건에서 5건을 고르는 랭킹 레이어. 임베딩 + 리랭커, Hit@5 / MRR / nDCG로 베이스라인 대비 개선폭 측정.
2. **생성 결과를 다른 모델로 검증하는 게이트를 넣었다** — 요약이 원문을 왜곡했는지 채점하고, 기준 미달이면 재생성. 생성자와 검증자를 분리.
3. **사용 로그가 랭킹으로 환류되는 구조를 만들었다** — 읽음/스킵 라벨을 축적해 관심사 프로파일을 갱신. 쓸수록 좋아지는 시스템.

**1~3 없이 만들면 이 프로젝트는 포트폴리오 가치가 없습니다.** 수집·요약·발행만 하는 봇은 이미 수백 개 있습니다.

## 2. 핵심 설계 판단 — 두 시스템을 하나로 만듭니다

논문 리뷰와 채용공고 정리는 **같은 파이프라인**입니다.

```
수집 → 중복 제거 → 관심사 기반 랭킹 → LLM 요약 → 검증 → 발행/푸시 → 피드백 축적
```

다른 것은 **소스 어댑터**와 **출력 템플릿**뿐입니다. 따라서 저장소 하나에 파이프라인 하나, 채널 둘(`papers`, `jobs`)로 구현합니다.

**이 판단 자체가 포트폴리오의 일부입니다.** 면접에서 "왜 두 개를 따로 안 만들었나"에 대해 "수집 소스와 출력 형식만 다르고 중간 4단계가 동일해서 어댑터 패턴으로 분리했다, 세 번째 소스를 붙이는 데 걸린 시간이 X시간이다"라고 답할 수 있으면 그게 설계 역량의 증거입니다.

### 단, 발행 단계에서 갈립니다 (중요)

| 채널 | 공개 발행 | 이유 |
|:--|:--|:--|
| `papers` | **가능** | arXiv 초록은 재배포 가능한 라이선스가 다수. 요약은 2차 저작물로 본인 저작. |
| `jobs` | **금지 — 개인 수신 전용** | 채용공고 데이터를 수집해 공개 게시하면 §3의 판례 사안과 같은 구조가 됩니다. |

`jobs` 채널은 텔레그램 개인 푸시 + 로컬 저장까지만. **블로그·GitHub Pages·공개 저장소에 공고 내용을 커밋하지 않습니다.** 공개 저장소에는 코드와 통계(건수, 처리시간)만 올라갑니다.

## 3. 법적·약관 제약 (채용공고 채널)

### 3.1 크롤링 금지 — 근거 있는 실제 리스크

잡코리아가 사람인을 상대로 제기한 채용정보 무단 크롤링 사건에서, 법원은 **저작권법상 데이터베이스제작자의 권리 침해**를 인정했습니다. 2심 승소 후 최종 확정되었고, **120억 원 규모의 합의**로 마무리되었습니다.

이건 "약관 위반이라 계정 정지" 수준이 아니라 **데이터베이스제작자 권리 침해로 인한 손해배상** 사안입니다. 크롤링한 데이터를 공개 서비스로 재게시할 때 특히 위험합니다.

**따라서 다음 사이트는 스크래핑하지 않습니다.**

- 잡코리아 / **알바몬**(잡코리아 계열)
- 원티드, 리멤버, 링크드인 — 약관상 자동 수집 금지
- 사람인 **웹페이지** (API는 허용, §3.2)

### 3.2 공식 API만 사용합니다

| 소스 | 방식 | 조건 | 비고 |
|:--|:--|:--|:--|
| **사람인 채용정보 API** | `GET https://oapi.saramin.co.kr/job-search` | `access-key` 발급 필요, **1일 500회** | `count` 최대 110, `sort=pd`(게시일 역순), `published_min/max`로 전날 신규만 필터 가능 |
| **워크넷(고용24) 채용정보** | 공공데이터포털 오픈API | 무료, 활용신청 | 공공·중소기업 물량이 큼 |
| **개별 기업 채용 페이지** | 직접 조회 | robots.txt 준수, 1일 1회 이하 | 카카오뱅크·토스·네이버 등 관심 기업만 화이트리스트로 |

사람인 API 하루 500회면 충분합니다. 직무코드 5~10개 × 페이지 2~3회 = 30회 내외.

> **구현 전 확인 필요:** 사람인 API 이용신청 시 제시되는 약관에서 **데이터 저장·재배포 조항**을 직접 확인할 것. 문서에 명시가 없어 `api@saramin.co.kr` 문의가 필요할 수 있습니다. 개인 수신용이면 통상 문제없지만, 확인 없이 진행하지 마세요.

### 3.3 논문 채널은 제약이 훨씬 가볍습니다

- **arXiv API**: `http://export.arxiv.org/api/query`, 키 불필요. 권장 호출 간격 **3초에 1회**. 이 간격을 코드로 강제하세요.
- **Hugging Face Daily Papers**: 큐레이션된 하루 10~30편. 1차 후보로 유용.
- 원문 PDF 전문을 재배포하지 않습니다. 초록 + 본인 요약 + 원문 링크까지만 발행합니다.

## 5. 기술 스택 (확정)

| 레이어 | 선택 | 근거 |
|:--|:--|:--|
| 언어 | Python 3.11 | — |
| 실행 환경 | **GitHub Actions cron** (public repo) | 서버 비용 0원. 실행 로그가 공개돼 "매일 실제로 돈다"가 증명됨 |
| 1차 임베딩 | **API 임베딩** (OpenAI `text-embedding-3-small` 등) | Actions 러너는 **4 vCPU · GPU 없음**. 로컬 모델로 500건 인코딩은 10분 이상 소요. API는 하루 수십 원 수준 |
| 2차 리랭커 | **`BAAI/bge-reranker-v2-m3`** (로컬 CPU) | 30쌍만 처리하므로 CPU로 1분 이내. **BidMate에서 이미 사용한 모델 — 경험 재사용이 설명 가능** |
| 벡터 저장 | ChromaDB (persistent) | BidMate 경험 재사용. 90일치 약 3만 건이면 충분 |
| 요약 생성 | Claude API | forG에서 사용 중 |
| 요약 검증 | **다른 계열 모델** (OpenRouter 경유) | 생성자와 검증자를 분리하지 않으면 검증이 성립하지 않음 (forG-mini에서 확립한 원칙) |
| 상태 관리 | SQLite (`state.db`) + JSONL 원장 | Actions 단발 실행이라 PostgreSQL 불필요. **원장 패턴은 AdNova `runs.jsonl` 계승** |
| 정적 사이트 | **Hugo + PaperMod** | 빌드 수초. GitHub Pages 배포 액션 존재 |
| 푸시 | python-telegram-bot | forG 봇 코드 재사용 |
| 테스트/게이트 | pytest | **AdNova의 "실패를 pytest 게이트로 전환" 패턴 계승** |

### 5.1 결정이 필요했던 지점 두 개

**(1) 임베딩을 로컬에서 돌릴 것인가**
→ 안 돌립니다. Actions 러너에 GPU가 없고, bge-m3급 모델로 500건을 CPU 인코딩하면 실행시간의 대부분을 잡아먹습니다. 1차는 API, 2차 리랭커만 로컬. **비용 대비 시간 트레이드오프를 명시적으로 계산한 판단**이므로 문서에 근거를 남기세요.

**(2) 텔레그램 인라인 버튼 콜백을 어떻게 받을 것인가**
Actions는 단발 실행이라 webhook 상시 수신이 불가능합니다.
→ **다음날 실행 시 `getUpdates`로 지난 24시간 콜백을 일괄 수집**합니다. 텔레그램은 업데이트를 24시간 보관하므로 하루 1회 배치 수집으로 충분합니다. 피드백은 랭킹 개선용이라 하루 지연이 문제되지 않습니다.
- 제약: webhook이 설정돼 있으면 `getUpdates`가 동작하지 않습니다. 봇을 분리하거나 webhook을 해제하세요.
- 실행이 하루 실패하면 그날 피드백은 유실됩니다. 유실을 원장에 기록하고 넘어갑니다.
- (대안) forG 서버가 상시 가동 중이면 그쪽에 webhook을 붙일 수 있으나, 저장소 자립성이 떨어지므로 기본안은 폴링입니다.

## 7. 데이터 스키마

### `data/profile.papers.yaml` / `data/profile.jobs.yaml` — 관심사 시드

**작성 완료. 별도 파일로 전달되었으므로 그대로 `data/`에 넣으세요.** 아래는 설계 근거입니다.

**(1) 파일을 둘로 나눈 이유 — 노출**
채용 프로파일에는 희망 연차·지역·제외 조건이 들어갑니다. 공개 저장소에 올리면 본인의 구직 조건이 그대로 노출됩니다. `profile.jobs.yaml`은 `.gitignore`에 등록하고, Actions에서는 Secret `PROFILE_JOBS_YAML`에 base64로 넣어 런타임에 복원합니다.

**(2) 프로파일 언어를 소스 언어에 맞춘 이유 — 랭킹 성능** ★
- `profile.papers.yaml`은 **영어**로 작성했습니다. arXiv 초록이 영어이기 때문입니다. 다국어 임베딩 모델이라도 교차언어 정렬은 동일언어 대비 약하므로, 한국어 프로파일로 영어 초록을 검색하면 성능이 떨어집니다.
- `profile.jobs.yaml`은 **한국어**입니다. 국내 채용공고가 한국어이기 때문입니다.
- **M1 평가에서 이 가정을 검증하세요.** 한국어 프로파일 버전을 추가 조건으로 넣어 Hit@5를 비교하면, 교차언어 손실을 실측한 근거가 됩니다. 이건 포트폴리오에 쓸 수 있는 실험입니다.

**(3) `text` 필드는 키워드가 아니라 서술문입니다**
임베딩은 문맥을 봅니다. `"diffusion, mask, editing"`보다 `"image editing with diffusion models while preserving object identity"`가 초록과 잘 맞습니다. `label`은 사람이 읽기 위한 필드이므로 임베딩하지 마세요.

**(4) `exclude`는 하드 배제가 아니라 감점입니다**
경계 사례를 통째로 버리지 않기 위함입니다. 단 `profile.jobs.yaml`의 `exclude_keywords.hard`는 즉시 제외입니다.

## 8. 마일스톤 및 완료 조건(DoD)

> 각 마일스톤은 **독립적으로 동작하는 상태**로 끝나야 합니다. DoD를 만족하지 못하면 다음으로 넘어가지 않습니다.

### M0 — 뼈대 + 논문 수집
- `SourceAdapter` 인터페이스 정의, `arxiv.py` 구현
- arXiv API 호출 간격 3초 강제 (코드 레벨)
- 하루치 후보를 `data/candidates/{date}.jsonl`로 저장
- **DoD:** `python -m src.core.pipeline --channel papers --stage collect` 실행 시 300건 이상 수집, `runs.jsonl`에 1줄 기록, 재실행 시 중복 0건

### M1 — 랭킹 레이어 + 정량 평가 ★ 포트폴리오 핵심
- `profile.yaml` 임베딩 → 후보 임베딩 → 코사인 유사도 top 30
- `bge-reranker-v2-m3`로 top 30 → top 5
- 골드셋 구축(§9) 후 `eval/run_eval.py`로 성능 측정
- **DoD:** 골드셋에서 **Hit@5 / MRR / nDCG@10** 측정치가 나오고, **키워드 매칭 베이스라인 대비 개선폭이 수치로 기록**됨. 결과를 `eval/results.md`에 표로 남길 것

### M2 — 요약 + 검증 게이트 ★ 포트폴리오 핵심
- 구조화 요약 프롬프트: `문제 / 방법 / 핵심 결과(수치 포함) / 한계 / 내 프로젝트와의 연결점`
- `faithfulness.py`: 원문 초록과 요약을 **다른 계열 모델**에 주고, 요약 내 각 주장이 원문에 근거하는지 채점 (0~1) + 미근거 주장 목록 반환
- 검증자 프롬프트는 **문제를 찾도록** 지시할 것. "확인해줘"가 아니라 "근거 없는 주장을 찾아라"
- 임계 0.7 미만 → 재생성 (최대 2회) → 그래도 미달이면 경고 플래그와 함께 발행하고 원장에 기록
- **DoD:** 20건 샘플에서 faithfulness 분포와 재생성 발생률이 `runs.jsonl`에 기록됨. 의도적으로 왜곡한 요약 3건을 검증자가 모두 잡아내는 테스트 통과

### M3 — 발행 + 자동화
- Hugo 프론트매터 포함 Markdown 생성 → `site/content/posts/`
- git commit + push, GitHub Pages 배포
- `daily-papers.yml` cron 등록 (07:00 KST = `0 22 * * *` UTC)
- **DoD:** 사람 개입 없이 3일 연속 성공 실행. Pages에 3개 포스트 게시 확인

### M4 — 텔레그램 푸시 + 피드백 수집
- 요약 5건을 인라인 버튼(읽음/스킵/저장)과 함께 푸시
- 다음 실행 시 `getUpdates`로 지난 24시간 콜백 수집 → `feedback.jsonl`
- **DoD:** 버튼 클릭이 다음날 실행에서 `feedback.jsonl`에 정확히 기록됨

### M5 — 채용공고 채널
- `saramin.py`: `published_min/max`로 전날 신규만, `sort=pd`, `count=110`
- **일 500회 호출 한도 준수** — 호출 카운터를 코드로 강제
- `worknet.py`: 공공데이터포털 API
- 출력은 **텔레그램 전용**. `data/jobs/`는 `.gitignore`에 등록
- **DoD:** 공고 원문이 git에 단 한 줄도 커밋되지 않음을 테스트로 검증(`test_gates.py::test_jobs_never_committed`). 전날 신규 공고만 정확히 수집됨

### M6 — 피드백 환류
- `feedback.jsonl` 누적 라벨로 `profile.yaml`의 관심사 가중치 갱신
- 갱신 전후 랭킹 성능을 골드셋으로 재측정
- **DoD:** 라벨 50건 이상 누적 후 갱신 적용, 성능 변화가 `eval/results.md`에 기록됨 (개선/악화 무관하게 사실대로)

## 9. 평가 설계 (M1 선행 작업)

**포트폴리오에서 가장 중요한 부분입니다.** "잘 고른다"는 주장이 아니라 측정치가 필요합니다.

### 골드셋 구축 절차
1. 3일치 논문 후보를 수집 (약 900~1,500건)
2. 각 날짜별로 **본인이 직접** 관련 논문을 표시. 하루 3~7건 예상
3. `eval/goldset.yaml`에 `{date, item_id, relevant: true/false}` 형태로 저장
4. 라벨링 기준을 문서로 남길 것 — "왜 이걸 관련 있다고 했는가"가 없으면 재현 불가

### 측정 지표
- **Hit@5**: 정답이 상위 5건에 포함된 비율
- **MRR**: 첫 정답의 역순위 평균
- **nDCG@10**

### 비교 대상 (최소 3개 이상)
| 조건 | 설명 |
|:--|:--|
| 베이스라인 | 프로파일 키워드 문자열 매칭 |
| 임베딩만 | 1차 필터만, 리랭커 없음 |
| 임베딩 + 리랭커 | 최종 구성 |
| (선택) 임베딩 모델 교체 | BidMate의 12조합 비교 방식 축소판 |

결과는 `eval/results.md`에 표로. **개선폭이 작거나 없으면 그것도 그대로 기록합니다.** 나중에 면접에서 "왜 리랭커를 넣었나"에 답할 근거가 됩니다.

## 10. 실패 게이트 (pytest)

AdNova에서 확립한 "실패를 게이트로 전환" 패턴을 그대로 적용합니다. 게이트 실패 시 Actions 실행이 **빨간불로 남아야** 합니다. 조용히 넘어가면 안 됩니다.

```
test_collect_nonzero          수집 0건이면 실패
test_no_duplicates            선정 결과에 동일 item_id 중복 시 실패
test_faithfulness_threshold   임계 미달 요약이 플래그 없이 발행되면 실패
test_frontmatter_schema       Hugo 프론트매터 필수 필드 누락 시 실패
test_jobs_never_committed     data/jobs/ 하위 파일이 git에 추적되면 실패  ★
test_jobs_profile_ignored     data/profile.jobs.yaml이 git에 추적되면 실패 ★
test_saramin_rate_limit       일일 호출 카운터가 500 초과 시 실패        ★
test_arxiv_interval           arXiv 호출 간격 3초 미만이면 실패           ★
test_verifier_differs         검증자 모델 ID가 생성자와 같으면 실패       ★
```

★ 표시는 법적·설계 원칙에 직결되는 게이트입니다. 비활성화하지 마세요.
