## ① 원장 스키마 `stage` 키 — **승인. 단 조건 있음**

### 승인 이유
`stage` 없이는 `summaries: []`가 **"수집만 했다"인지 "전체 실행했는데 0건 선정됐다"인지 구분되지 않습니다.** 기획안 §12가 요구하는 "90일 무중단 자동 실행 — 성공률 N%"를 계산할 때 이 둘을 섞으면 수치가 거짓이 됩니다. 운영 지표를 위해 필요한 키입니다.

### 조건 3개

**(1) `schema` 를 2로 올리지 마세요. 1 그대로입니다.**
§7의 "스키마 변경 시 버전을 올린다"는 **이미 기록된 줄이 있을 때** 적용됩니다. 지금은 `runs.jsonl`이 존재하지 않습니다. **`stage`를 포함한 형태가 schema 1의 원형**이 됩니다. 버전을 2로 시작하면 세상에 없는 schema 1을 영원히 처리하는 리더 코드를 짜게 됩니다.

**(2) 미실행 단계는 키 삭제가 아니라 `null`.** 제안하신 대로입니다. 리더가 `row["selected"]`에서 KeyError를 내지 않습니다.

**(3) `stage` 허용값을 지금 고정하세요.** 안 그러면 나중에 `"collect_only"`, `"COLLECT"` 같은 변종이 섞입니다.

```
"stage": "collect" | "rank" | "summarize" | "publish" | "full"
```

`--stage`를 안 주고 전 구간 실행하면 `"full"`입니다. 이 5개 외의 값이 들어가면 `ledger.py`가 예외를 던지게 하세요.

판단이 맞습니다. HF Daily Papers는 **공식 문서화된 API 엔드포인트가 아닙니다.** CLAUDE.md §3-5는 "공식 API만 사용"이고, 문서화되지 않은 내부 엔드포인트를 추측으로 붙이는 건 그 원칙에 걸립니다. 예고 없이 바뀌어도 항의할 근거가 없습니다.

**추가 요구**: `data/profile.papers.yaml`의 `sources.hf_daily_papers.enabled`가 `true`인데, 이제 사실과 다릅니다. **설정이 코드와 어긋난 채로 남으면 다음 사람이 "왜 안 도나"로 시간을 씁니다.** 아래로 고치세요.

```yaml
  hf_daily_papers:
    enabled: false
    # 보류: 공식 문서화된 API 엔드포인트가 아님 (CLAUDE.md §3-5).
    # 붙이려면 이용약관·엔드포인트 안정성을 먼저 확인받을 것.
    note: "큐레이션된 하루 10~30편. 1차 후보 보강용"
```

수정본 파일명은 **④의 결론에 따릅니다.**

## ④ ★ 파일 번호 규칙이 설정 로더를 깨뜨립니다 — 지금 정해야 합니다

제기되지 않았지만 `config.py`를 쓰기 전에 정해야 합니다.

**문제**: 이 저장소 규칙은 "파일을 고치면 덮어쓰지 않고 `_N`을 붙여 새로 저장, 읽을 땐 최고 번호"입니다. 그런데 **코드가 설정을 경로로 로드**합니다. `data/profile.jobs.yaml`을 하드코딩해두면 이미 존재하는 `profile.jobs_1.yaml`(최신)을 못 읽고 구버전을 읽습니다. **지금 당장 틀린 상태입니다.** M5에서 `_2`가 생기면 더 나빠집니다.

**결정: 로더가 최고 번호를 해석합니다.**

```python
# src/core/config.py
def resolve_profile(stem: str, ext: str = ".yaml", root: Path = Path("data")) -> Path:
    """'profile.jobs' → data/profile.jobs_2.yaml (최고 번호). 번호 없는 파일은 0으로 취급."""
    cands = []
    for p in root.glob(f"{stem}*{ext}"):
        rest = p.name[len(stem):-len(ext)]
        if rest == "":
            cands.append((0, p))
        elif rest.startswith("_") and rest[1:].isdigit():
            cands.append((int(rest[1:]), p))
    if not cands:
        raise FileNotFoundError(f"{root}/{stem}*{ext}")
    return max(cands)[1]
```

- **접미사 없는 파일은 0** — 가장 오래된 것. 관측된 현실(`profile.jobs.yaml` 구버전 → `_1` 최신)과 일치합니다
- `profile.papers.ko.yaml`이 `stem="profile.papers"`에 걸리지 않도록 정규식을 `_숫자`로 엄격히 제한하세요. 위 구현은 `.ko`가 `_숫자`가 아니라 제외됩니다
- **로드한 실제 경로를 원장(`runs.jsonl`)에 기록하세요.** 어느 프로파일로 돈 결과인지 나중에 못 밝히면 §9 평가가 재현 불가가 됩니다

**테스트 추가**: `test_profile_resolution` — 임시 디렉터리에 `x.yaml`, `x_1.yaml`, `x_10.yaml`, `x.ko.yaml`을 만들고 `x_10.yaml`이 선택되는지. **`x_10` > `x_9`** (문자열 정렬이면 틀립니다) 와 `.ko` 미선택을 반드시 포함하세요.

> 대안은 "설정 파일만 번호 규칙에서 제외(git이 이력 관리)"였는데, `profile.jobs*`는 gitignore라 git 이력이 없습니다. 번호가 유일한 이력이므로 제외하면 안 됩니다.

## ⑥ DoD 300건 — 측정 지점만 명확히

`cs.CL/CV/LG/IR/AI` 5개 카테고리면 평일 400~600건이 나오는 게 맞습니다. 다만 **48시간 창을 클라이언트에서 적용한 뒤에도 300건인지**가 관건입니다. 연휴가 길면 하락할 수 있습니다.

**DoD의 300건은 "48시간 창 적용 후, 중복 제거 전" 기준으로 측정하세요.** 원장에 `collected`(창 적용 후)와 `after_dedup`을 따로 기록하는 §7 스키마가 이미 그 구분을 전제하고 있습니다. 연휴로 미달하면 실패가 아니라 **창을 72시간으로 넓히고 그 사실을 원장에 남기면** 됩니다.
