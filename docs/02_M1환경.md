## 2. 실측치 — 기획안·델타의 추정을 검증했습니다

### 2.1 임베딩 (bge-m3, 1024차원)

| 장치 | 건당 | 719건 환산 |
|:--|--:|--:|
| CPU (6 threads) | 0.255s | **3.1분** |
| MPS (Apple GPU) | 0.094s | **1.1분** |

델타 §D6.3의 추정 *"1건 약 0.2초, 1,000건 약 3~4분"* → **CPU 기준으로 정확했습니다.**

### 2.2 리랭킹 (bge-reranker-v2-m3)

30쌍 환산 **31.5초**. 기획안 §5의 *"30쌍만 처리하므로 CPU로 1분 이내"* → **확인됨.**

### 2.3 MPS를 써도 되는가 — 확인했습니다

속도만 보고 MPS를 권하면 함정일 수 있어서 CPU와 같은 값을 내는지 검증했습니다.

```
cpu↔mps 코사인 유사도   최소 1.000000 · 평균 1.000000
최대 절대오차            5.22e-07   (float32 반올림 수준)
랭킹 순위                완전 일치 (top-5 포함)
```

**써도 됩니다.** 다만 `eval/results.md`에 **어느 장치로 돌렸는지 기록**하세요.
재현할 사람이 조건을 맞출 수 있어야 합니다.

M1은 4개 조건 × 3일치를 돌립니다. MPS면 임베딩만 12분 → 4분입니다.

## 3. ★ 밟은 함정 2개 — 둘 다 M1 수치를 조용히 망칠 뻔했습니다

### 3.1 미머지 PR의 가중치로 평가가 돌 뻔했습니다

`SentenceTransformer("BAAI/bge-m3")` 를 리비전 없이 호출했더니, sentence-transformers
5.x가 safetensors를 선호해서 **main이 아니라 머지되지 않은 PR(`refs/pr/130`)에서
가중치를 받아갔습니다.**

```
rev 9a0624b896d8  refs=['refs/pr/130']  2.27GB  ['model.safetensors']   ← ST가 쓴 것
rev 5617a9f61b02  refs=['main']         2.31GB  ['pytorch_model.bin', ...]
```

캐시에 2.3GB가 중복으로 쌓인 건 부차적입니다. **진짜 문제는 재현성입니다.**
PR은 닫히거나 바뀔 수 있고, 그 상태로 낸 Hit@5는 3개월 뒤에 재현되지 않습니다.
M1 수치가 이 프로젝트의 포트폴리오 가치 전부인데(기획안 §1) 재현이 안 되면 의미가 없습니다.

**조치**
- 미머지 PR 리비전 삭제 (2.3GB 회수). 제 명령이 유발한 중복이라 정리했습니다
- `eval/models.yaml`에 **커밋 해시로 리비전 고정**
- `test_eval_models_are_revision_pinned` 게이트 추가 — 40자 해시가 아니면 실패
- `HF_HUB_OFFLINE=1`로 재검증: 재다운로드 없이 로드되고 캐시 크기 불변

### 3.2 CrossEncoder가 기본으로 sigmoid를 씌웁니다

같은 5쌍에 대한 출력입니다.

| 설정 | 범위 | 표준편차 |
|:--|:--|--:|
| 기본값 | `+0.0000 ~ +0.0751` | 0.029 |
| `activation_fn=Identity()` | `-10.08 ~ -2.51` | 2.92 |

순위는 단조변환이라 **동일합니다.** 문제는 두 가지입니다.

1. 무관한 쌍이 전부 0 근처에 뭉쳐서 원장 `rank_score_stage2`에 남겨도 **사람이 읽을 수가
   없습니다.** `0.0000`과 `0.0001`이 로짓으로는 -9.2와 -9.0입니다
2. `selection.min_score_threshold` 를 정할 때 로짓이 훨씬 다루기 쉽습니다

→ `eval/models.yaml`에 `use_raw_logits: true`로 기록했습니다.

## 4. 의존성을 두 파일로 분리했습니다 ★

```
requirements.txt        운영 (Actions 매일)  — PyYAML, requests, pytest
requirements-eval.txt   평가 (로컬 1회성)    — torch, sentence-transformers, transformers
```

기획안 §5.1-(1)은 *"Actions 러너에서 로컬 임베딩을 돌리지 않는다"*고 결정했고 그 결정은
유효합니다. 그런데 M1 **평가**는 Actions가 아니라 로컬 배치라 로컬 임베딩을 씁니다
(델타 §D6.3). 두 사실이 충돌하지 않으려면 의존성이 분리돼야 합니다.

**한 파일에 두면 매일 도는 워크플로가 매번 torch 1GB를 설치합니다.**

`test_actions_requirements_have_no_local_models` 가 이 분리를 강제합니다. 나중에 누가
편의상 합치면 빨간불이 납니다.

## 5. 공짜로 얻은 5번째 비교 조건

캐시를 뒤지다 발견했습니다 — **`nlpai-lab/KURE-v1`(2.1GB)이 이미 있습니다.**

BidMate에서 쓰신 한국어 특화 임베딩이고, `profile.papers_1.yaml`의 관심사
`multilingual_korean_retrieval`이 바로 이 경험에서 나온 항목입니다
(`origin: "BidMate — KURE-v1"`).

기획안 §9의 비교 조건 *"(선택) 임베딩 모델 교체"* 를 **추가 다운로드 0으로** 채울 수
있습니다. 게다가 델타 §D6.3의 4번 조건(영/한 프로파일 비교)과 곱하면 2×2가 됩니다.

| | bge-m3 (다국어) | KURE-v1 (한국어 특화) |
|:--|:--:|:--:|
| 영어 프로파일 | 기준 | ? |
| 한국어 프로파일 | ? | ? |

영어 초록에 한국어 특화 모델을 쓰면 어떻게 되는지가 나옵니다. **교차언어 손실을
"프로파일 언어" 축과 "모델 특화 언어" 축으로 분리**하는 실험이고, 비용은 인코딩
시간뿐입니다(MPS로 조건당 1.1분).

`eval/models.yaml`의 `optional_embedders`에 리비전까지 고정해 뒀습니다.
**넣을지 말지는 본인 판단입니다** — 조건이 늘면 `eval/results.md` 표가 복잡해지고,
기획안 §9는 최소 3개를 요구하는데 이미 4개가 확보돼 있습니다.
