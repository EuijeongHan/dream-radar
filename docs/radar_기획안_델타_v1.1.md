## D1. arXiv 라이선스 — v1.0 §2의 근거가 틀렸습니다 ★

v1.0 §2 발행 표에 이렇게 썼습니다.

> `papers` 공개 가능 — "arXiv 초록은 재배포 가능한 라이선스가 다수. 요약은 2차 저작물로 본인 저작."

**결론은 맞지만 근거가 틀렸습니다.** arXiv 공식 문서를 확인한 결과는 이렇습니다.

| 대상 | 실제 라이선스 | 제3자 이용 |
|:--|:--|:--|
| **서술 메타데이터** (제목·초록·저자·분류) | **CC0 1.0 Public Domain Dedication** — arXiv API 이용약관에 명시 | 저장·가공·번역·재배포·상업적 이용 **전부 자유. 출처 표기 의무조차 없음** |
| **전문** (PDF·소스) | **논문별로 다름.** 대부분은 arXiv 비독점 라이선스이고, 이 라이선스는 "다른 주체·개인의 모든 유형의 재이용을 제한"합니다 | **자체 서버에 저장·서빙 금지.** CC 계열 라이선스가 붙은 소수만 예외 |

즉 "재배포 가능한 라이선스가 다수"인 게 아닙니다. **다수는 재배포 불가이고, 우리가 쓰는 초록이 별도로 CC0인 것**입니다.

### 왜 이 구분이 중요한가

결론이 같으니 넘어가도 될 것 같지만, 세 가지가 달라집니다.

**(1) 하지 말아야 할 것이 명확해집니다.** "라이선스가 관대하다"고 이해하면 언젠가 "전문을 읽고 요약하면 더 좋겠는데"가 됩니다. 그건 금지입니다. **PDF는 다운로드도, 캐시도 하지 않습니다.** 편의상의 선택이 아니라 라이선스 준수 조치이므로 코드 주석에 근거를 남기세요.

**(2) "요약은 2차 저작물로 본인 저작"이라는 논리가 불필요해집니다.** 원문이 CC0이면 2차 저작물 여부를 따질 필요가 없습니다. 더 튼튼한 근거로 교체됩니다.

**(3) 라이선스 게이트를 지금 넣어야 합니다.** 나중에 전문을 쓰고 싶어질 때를 대비합니다.

### 구현 요구사항 — 라이선스 게이트

**라이선스 필드는 Search API 스키마에 없고, OAI-PMH 출력에만 있습니다.** 따라서 수집기를 2계통으로 둡니다.

```
Search API   → 검색·랭킹용 (초록까지)          — 후보 전체
OAI-PMH      → 라이선스 확인용                  — 선정된 top-N 에만
```

100건 전부 OAI-PMH를 조회하면 3초 간격 × 100 = 300초입니다. **선정된 5건에만** 조회하세요.

```python
FULLTEXT_OK = {
    "http://creativecommons.org/publicdomain/zero/1.0/",
    "http://creativecommons.org/licenses/by/4.0/",
    "http://creativecommons.org/licenses/by-sa/4.0/",
}
item.fulltext_ok = license_uri in FULLTEXT_OK   # 기본값 False
```

현재 파이프라인은 `fulltext_ok`를 **읽기만 하고 쓰지 않습니다.** 전문을 쓰는 코드가 없기 때문입니다. 이 필드는 미래의 자기 자신을 막기 위한 장치입니다.

### 원문 링크 의무

arXiv 이용약관 권고: *"Direct users to arXiv.org to retrieve e-print content."*
→ 모든 산출물(텔레그램 메시지, Hugo 포스트)에 `abs` 페이지 링크 필수. `test_frontmatter_schema`에 링크 필드 검사를 추가하세요.

## D2. arXiv 호출 제약 — 권장이 아니라 요구사항입니다

v1.0 §3.3: *"권장 호출 간격 3초에 1회"*

실제 약관 문구는 이렇습니다.

> "Make no more than one request every three seconds, **and limit requests to a single connection at a time.**"
> 이 제약은 "**본인 통제 하의 모든 머신에 합산 적용**"됩니다.

정정 사항 3개:

1. **권장이 아닙니다.** 위반 시 IP 차단입니다.
2. **단일 커넥션 제약이 추가입니다.** v1.0에는 이 항목이 빠져 있습니다. 3초 간격만 지키고 병렬로 3개를 동시에 던지면 위반입니다. **수집기에 병렬화를 넣지 마세요.**
3. **머신 합산입니다.** 로컬에서 개발 테스트를 돌리는 동안 Actions 크론이 겹치면 합산 위반입니다. 개발 중에는 크론을 꺼두거나, 로컬 테스트는 캐시된 픽스처로 하세요.

`test_arxiv_interval`에 커넥션 수 검사를 추가합니다 → D8.

## D4. 게시 정책 — "노션이나 블로그에 비공개로 올려도 되나"

### 답: 형태에 따라 다릅니다. 약관보다 형태가 문제입니다.

| 형태 | 판정 | 근거 |
|:--|:--|:--|
| 노션 페이지, **공유 해제 상태** | **가능** | 개인 저장의 연장. 제3자 접근 없음. 조항 어디에도 걸리지 않음 |
| 노션 **"웹에 게시"** 링크 | **비공개가 아닙니다** | 링크만 알면 누구나 열람하고 검색엔진 색인 대상. 이건 공개 배포입니다 |
| 블로그 비공개 글 | 가능 | 단 플랫폼이 초안을 색인하는 사고 사례가 있으니 신뢰하지 마세요 |
| **광고 붙은 블로그에 공개 게시** | **하지 마세요** | 조항 3. 트래픽 → 광고수익 경로가 생기면 "API 기반 서비스로 대가를 얻었다"는 해석이 가능합니다 |
| 공개 사이트에 **공고 목록** 게시 | **하지 마세요** | 조항 6. 사람인 공고를 모아 보여주면 제휴·집계 서비스로 오인될 수 있습니다. 무료여도 걸립니다 |

### "배포만 안 하면 된다"는 이해는 절반만 맞습니다

- 맞는 부분: **비공개 개인 저장은 아무 문제 없습니다.** 노션 비공개 아카이브는 v1.0 설계에 그대로 추가하면 됩니다.
- 틀린 부분: **무료 공개 게시도 조항 6에 걸립니다.** 돈을 안 받아도 "공고를 모아 보여주는 화면"은 그 자체로 오인 소지가 있습니다.

### 결정 (v1.0 §2 표를 이렇게 확장)

| 채널 | S1 텔레그램 | S2 비공개 아카이브 | S3 공개 사이트 |
|:--|:--:|:--:|:--:|
| `papers` | O | O | **O** |
| `jobs` | O | **O ← 신규 허용** | **X** |

**S2 신설이 이번 델타의 실질 변화입니다.** v1.0은 jobs를 "텔레그램 + 로컬 저장"까지로 봤는데, 노션 비공개 DB까지 확장 가능합니다. 지원 여부 추적과 라벨 축적에 로컬 SQLite보다 편합니다.

**S2 구현 요구사항**
- 노션 통합(Integration) 권한을 해당 DB **하나로만** 제한
- **"웹에 게시"를 켜지 않습니다.** 켜져 있으면 S3가 됩니다
- 배포 전 체크: 공유 상태를 코드로 확인할 수 없으므로 **README 체크리스트 + 월 1회 수동 확인** 항목으로 남깁니다

### 스코프 강제 (코드)

v1.0 §10의 게이트만으로는 부족합니다. 아이템 레벨에서 막습니다.

```python
# models.py
publish_scope: Literal["private", "public"]   # 소스 어댑터가 생성 시점에 채움
# saramin.py / worknet.py 는 "private" 리터럴만 낼 수 있게 합니다. 설정으로 못 바꿉니다.

# publish/pages.py
def publish_public(items):
    leaked = [i for i in items if i.publish_scope != "public"]
    if leaked:
        raise ScopeViolation(f"private item reached public sink: {[i.id for i in leaked]}")
```

### D5.2 변동성 경고 — 이걸 KPI로 삼으면 안 되는 이유

Semrush 데이터에서 **ChatGPT의 Reddit 인용이 2025년 9월 중순 약 60% → 약 10%로 급락**했습니다. Wikipedia도 약 55% → 20% 미만으로 떨어졌습니다. 플랫폼 파라미터 변경 한 번에 순위가 뒤집힙니다.

**통제 불가능한 지표입니다.** 랭킹 성능(Hit@5)은 우리가 개선할 수 있지만 인용 점유율은 아닙니다. §12 포트폴리오 지표에 넣지 마세요.

### D5.3 네이버 블로그가 특히 나쁜 이유

네이버 블로그는 robots.txt로 **GPTBot · PerplexityBot · Google-Extended 등 AI 학습·검색 크롤러 접근을 차단**하고 있습니다. 크롤러가 HTML을 받지 못하므로 AI가 원문을 읽는 경로 자체가 없습니다.

> **확인 필요**: 이 항목은 2차 출처(인블로그, 2026-06-20 수정) 기준입니다. `blog.naver.com/robots.txt` 직접 조회는 403으로 막혀 원문 확인을 못 했습니다. 네이버에 올릴 계획이 있으면 직접 확인하세요.

### D5.4 "논문은 가공해서 게시하고 싶다" → 가능합니다

D1에서 확인한 대로 **초록은 CC0 1.0**이므로 요약·번역·재구성 후 게시에 라이선스 제약이 없습니다. 출처 표기 의무조차 없습니다. 단 D1의 3원칙(전문 미러링 금지 / 라이선스 게이트 / 원문 링크)은 지킵니다.

### D5.5 공개 채널 선정 — v1.0 §5의 Hugo + Pages 유지

v1.0이 이미 정한 **Hugo + GitHub Pages**가 정답입니다. 네이버 블로그로 바꾸지 마세요. 두 가지만 추가합니다.

1. **`static/robots.txt`에서 AI 크롤러를 명시적으로 허용**합니다. 네이버가 차단하는 것과 반대로 갑니다.

2. **`/llms.txt` 제공** — 사이트 구조와 주요 페이지를 평문으로 요약한 파일.

### D5.6 현실적 기대치 (솔직하게)

신규 개인 도메인이 위 표의 점유율을 뚫을 확률은 낮습니다. 상위 2개 도메인이 25%를 가져가는 구조이고, 순위는 하룻밤에 뒤집힙니다.

**그래서 S3의 목적을 "AI 인용"이 아니라 "채용 담당자가 볼 수 있는 공개 산출물"로 잡습니다.**

- 진짜 차별점은 논문 요약이 아니라 **§9 평가 결과입니다.** 논문 요약 봇은 v1.0 §1에 쓴 대로 이미 수백 개 있습니다. `eval/results.md`의 비교표가 공개되는 게 이 사이트의 존재 이유입니다.
- AI 인용은 부수 효과로 둡니다. 굳이 노린다면: ① 크롤 가능한 자체 도메인에 원본 → ② Reddit·Hacker News에 재유통 → ③ 명확한 제목·정의문·표로 구조화. Wikipedia와 Fandom이 상위인 이유는 권위만이 아니라 **형식**입니다.

### D6.2 전제: Port/Adapter + Fake 기본값

모든 외부 의존을 프로토콜로 분리하고 **Fake 어댑터를 기본값**으로 둡니다. `RADAR_MODE=fake`면 키 0개로 수집→랭킹→요약→검증→발행 전 구간이 실행되고 pytest가 통과합니다.

```
                 ports              구현체
 sources     SourceAdapter     arxiv ✓키불필요 / saramin / worknet / fake ✓
 embed       Embedder          openai / local_bge ✓ / hash_stub ✓
 rerank      Reranker          bge-reranker-v2-m3 ✓키불필요(v1.0 §5에서 이미 로컬)
 generate    Generator         anthropic / fake ✓
 verify      Verifier          openrouter / rulebased_fake ✓
 publish     Sink              hugo ✓ / telegram / notion / file ✓
                                                        ✓ = 키 불필요
```

`hash_stub` 임베더는 의미가 없지만 **파이프라인 배선 테스트에는 충분합니다.** 랭킹 품질 테스트에는 `local_bge`를 씁니다.

### D6.3 M1을 키 없이 완주하는 방법 — v1.0 §5.1(1)과 충돌하지 않습니다

v1.0 §5.1(1)은 **"Actions 러너에서 로컬 임베딩을 돌리지 않는다"**고 결정했습니다. 이 결정은 유지합니다. 근거(4 vCPU·GPU 없음·500건 CPU 인코딩)가 여전히 타당합니다.

**하지만 M1의 평가는 Actions에서 돌리지 않습니다.** 골드셋 라벨링과 성능 측정은 본인 로컬 맥에서 한 번 돌리는 배치 작업입니다. 여기엔 위 제약이 적용되지 않습니다.

```
운영 (Actions, 매일)   : API 임베딩          ← v1.0 §5.1(1) 결정 유지
평가 (로컬, 1회성)     : bge-m3 로컬 임베딩   ← 지금 키 없이 가능
```

그리고 이건 **v1.0 §9의 비교 조건 "(선택) 임베딩 모델 교체"를 미리 채우는 것**이기도 합니다. 키가 도착하면 `text-embedding-3-small`을 네 번째 조건으로 추가만 하면 됩니다.

**지금 실행 가능한 M1 절차**

1. arXiv 3일치 수집 (키 불필요) → 약 900~1,500건
2. 본인이 직접 라벨링 → `eval/goldset.yaml`. **라벨링 기준을 문서로 남길 것** (v1.0 §9)
3. `bge-m3` 로컬 인코딩 (1건 약 0.2초, 1,000건 약 3~4분. 한 번 돌리고 캐시)
4. `bge-reranker-v2-m3` 리랭킹 — v1.0 §5에서 이미 로컬 CPU로 결정된 모델이라 **키가 원래 필요 없었습니다**
5. `eval/run_eval.py` → Hit@5 / MRR / nDCG@10

**비교 조건 (키 없이 4개 확보)**

| # | 조건 | 키 |
|:--:|:--|:--:|
| 1 | 키워드 문자열 매칭 (베이스라인) | 불필요 |
| 2 | bge-m3 임베딩만 | 불필요 |
| 3 | bge-m3 + bge-reranker (최종 구성) | 불필요 |
| 4 | **bge-m3(영어 프로파일) vs bge-m3(한국어 프로파일)** ← D7 | 불필요 |
| 5 | text-embedding-3-small + reranker | 키 필요, 나중 |

v1.0 §9는 "최소 3개"를 요구했는데 **키 없이 4개가 나옵니다.** DoD를 지금 만족할 수 있습니다.

### D6.4 M2를 키 없이 절반 하는 방법

키가 필요한 건 실제 생성·검증 호출뿐입니다. 나머지는 지금 확정합니다.

## D7. 추가 파일 2개

v1.0 §7이 "작성 완료, 별도 파일로 전달"이라고 한 `profile.papers.yaml`이 **`/Users/colourxswitch/radar/`에 없습니다.** 재작성해 함께 전달합니다.

| 파일 | 언어 | 용도 |
|:--|:--:|:--|
| `profile.papers.yaml` | 영어 | **운영용.** 관심사 15개(weight 1.0 다섯 / 0.9 넷 / 0.8 넷 / 0.6 둘). 각 항목에 `origin` 필드로 출처 프로젝트를 명시 |

**두 파일은 `id`·`weight`·순서·`exclude`가 완전히 동일합니다.** `text`만 번역했습니다. 그래야 랭킹 차이의 원인을 언어로 귀속할 수 있습니다 — 하나라도 다르면 교차언어 손실이 아니라 프로파일 차이를 재는 게 됩니다. 이 동일성은 `test_profile_parity`로 강제합니다(D8).

관심사는 임의 선정이 아니라 **포트폴리오 프로젝트 5건에서 도출**했습니다. 예: `text_rendering_cjk`는 AdNova에서 한글 철자 붕괴 때문에 조판을 PIL로 분리한 그 문제입니다. 관련 논문이 나오면 바로 걸립니다. 면접에서 "왜 이 관심사인가"에 답할 수 있어야 하므로 `origin` 필드를 지우지 마세요.

`profile.papers.yaml`에 추가된 설정 2개:
- `license_gate` — D1의 게이트
- `selection.min_score_threshold` — 고정 top-5가 아니라 임계 병행. **조용한 날 억지로 5건을 채우지 않습니다.** 초기값 0.42는 잠정치이고 M1 평가로 확정합니다
